# f.lux 功能对照与 OpenCareEyes 改进建议

核验日期：2026-10-09。依据 f.lux 官方 Windows 功能说明、更新记录、FAQ，以及本地 OpenCareEyes 0.10.0b5 的代码。当前完成研究与优先级整理，以下新增功能尚未实现。

## 结论

值得借鉴。f.lux 的主要参考价值在于围绕时间、作息和使用情境，让屏幕调节长期安静地工作。OpenCareEyes 已有日出日落、固定时间、应用例外、临时暂停和色温调节基础，应优先把这些能力做得平滑、容易理解，并验证实际生效和恢复。保留桌宠、休息提醒与专注的现有定位。

## 官方功能与现有实现

| 方面 | f.lux 官方资料 | OpenCareEyes 已有内容 | 建议改善 |
|---|---|---|---|
| 日程与作息 | 根据位置与起床时间安排光线，提供睡前模式。[功能说明](https://justgetflux.com/news/pages/v4/welcome/) | `core/scheduler.py` 支持日出日落和固定时间的日间/夜间方案，提供时间偏移及手动覆盖。 | 增加白天、傍晚、睡前三阶段，允许设置作息；用一条全天曲线说明当前和接下来的变化。 |
| 自然过渡 | 官方更新记录持续调整长渐变、日落时机及快速过渡；FAQ 提供快速过渡选项。[更新记录](https://justgetflux.com/news/pages/v4/readme/)、[FAQ](https://justgetflux.com/faq.html) | 调度按边界切换方案；`QueuedBlueLightFilter.request_temperature` 立即提交目标，50 ms 定时器只合并拖动预览请求。 | 自动变化采用连续过渡；拖动和临时恢复提供较快响应。进入暂停、手动调整和应用例外时可中断，结束后沿当前日程继续。 |

| 色温和亮度 | FAQ 区分调色温与环境亮度，笔记本建议优先调整背光。[FAQ](https://justgetflux.com/faq.html) | `ScreenDimmer` 是黑色透明遮罩的软件调暗；不是屏幕背光控制。 | 页面明确区分“色温”“软件调暗”“背光亮度”；将硬件背光作为后续独立能力，不把遮罩调暗描述为硬件亮度降低。 |

## 建议的实施顺序

1. **先验证屏幕效果的基本使用路径。** 对启用、临时停用、退出恢复、唤醒和外屏变化建立实机记录，再扩展自动化。模拟测试不能代替真实显示效果验收。
2. **连续过渡与三阶段作息一起做。** 沿用现有调度和效果协调入口，让日程只产生目标与过渡信息；由一个可取消的过渡过程推进。保留请求版本、最终提交确认及原色恢复，避免多个定时器同时写屏幕。
3. **增加只作用于色温的临时暂停。** 复用现有应用例外能力，补上清楚的托盘入口和自动恢复时刻。全局暂停继续保留，两个范围在状态中明确区分。
4. **简化屏幕页面。** 首屏只显示当前色温、当前状态、下一变化，以及调节和临时恢复入口；全天曲线可预览，位置、执行日和显示诊断放在展开区。
5. **最后考虑高级能力。** 每屏独立设置、硬件背光、灰阶阅读和外部灯光联动应在基础稳定后再排期。个人开发阶段不宜同时扩张这些硬件相关功能。

这些是基于现有代码的产品与实现建议，不是已完成的功能或相对 f.lux 的实测性能结论。f.lux 官方定位着重屏幕光线与作息；本项目的宣传也应描述具体能力，不从色温数值推导未经验证的护眼效果。

## 本机当前只读检测

2026-10-09 的本机只读探测能解析当前主显示器的稳定目标身份，HDR 关闭，能力结果为 `sdr_ready`。未读写 Gamma，未改变色温或亮度。这说明当前探测路径可用，不能据此证明色温已生效、色彩校准正确或热插拔恢复可靠。

历史日志中的显示身份识别失败仍保留为排查线索，不能直接写成当前必然故障。原始记录见本地交付目录 `验证/原版图标恢复-b5/display-readonly-probe.json`。

## 下一轮完成判据

- 日落、午夜、起床、夏令时和系统时间跳变后，目标色温与下一个事件正确；手动覆盖的结束规则明确。
- 连续过渡中手动调整、进入例外应用或暂停，不出现过时请求回写；暂停结束按当前时刻的计划恢复。
- “仅暂停色温”期间，休息倒计时与专注状态持续正常，界面显示恢复时刻。
- 休眠唤醒、屏幕插拔和关闭程序后，原始色彩保持或正确恢复；能力不足的显示器明确报告状态。
- 首屏能回答“现在是什么效果、为什么、何时变化、怎么临时恢复”；高级项不挤占主要操作。
